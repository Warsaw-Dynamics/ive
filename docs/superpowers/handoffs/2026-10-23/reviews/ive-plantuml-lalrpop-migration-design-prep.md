# PlantUML LALRPOP migration — architectural preparation

Prepared read-only on 2026-10-23 for the controller. This is a builder input, not an implementation, approved plan, or compatibility claim. No product files, dependency state, Git state, tests, reference oracles, or application instances were changed/run. Paths below are relative to `/mnt/data/Projects/ive/.worktree/diagram-ports/diagram-ports/` unless explicitly absolute. Inspection began at committed `40b949a278fcc2747316c0cfd182b23add4685cb`; the controller's subsequent shared comment-delimiter fix is deliberately not designed away. Implementation must start from its independently reviewed successor.

## Intent and constraints

The owner's instruction is to use LALRPOP for parsing PlantUML and rewrite the current ad-hoc parser. That means generated productions must recognize the actual existing language: wrappers, admitted preamble/styles, the admitted literal-definition declaration, and every currently implemented family. Putting `Line*` in a grammar and calling the existing line parsers is explicitly insufficient. Migrating only the next EBNF/regex family is also insufficient.

Preserve the investment below syntax: typed models, source-order identities and ownership, semantic validation, layout algorithms, measured text, scenes, safe SVG, public API, fixtures, and native viewer/worker behavior. The target remains the *currently admitted subset*, with the four explicitly assigned syntax-boundary repairs below. This does not add full PlantUML grammar, full TIM, complete Creole/styles, assets, or Graphviz parity.

Binding sources read: `/mnt/data/Projects/ive/progress.md`; `/mnt/data/Projects/ive/docs/superpowers/specs/2026-10-22-diagram-ports-implementation-design.md`; `/mnt/data/Projects/ive/.worktree/diagram-ports/.superpowers/sdd/2026-10-22-diagram-ports-plan/native-global-constraints.md`. In particular: one product implementer, independent controller review between increments, GPUI-free caller-memory engine, no runtime file/network/environment/process/JVM/JS/browser/dot, whole-input consumption, bounded work/retention/depth before allocations, meaningful RED/GREEN, unchanged actual native/fallback reporting, and only the authorized MIT PlantUML 1.2026.9 translation sources. Parser infrastructure dependencies may be separately audited permissive crates; that does not change the MIT-only PlantUML semantic-source rule.

## Approaches and recommendation

1. **One generated universal grammar and a new universal model.** It could remove dispatch, but conflates incompatible lexical domains (Salt columns, YAML indentation, JSON, labels, UML commands), expands ambiguity, and needlessly replaces stable model/layout contracts. Reject for this migration.
2. **Shared generated document/front matter plus generated family grammars, bounded custom lexers, typed syntax/semantic builders, sequential cutovers. Recommended.** Use one explicit syntax authority per migrated family, preserve existing models and layouts, and share lexical/span/budget machinery. Family-specific lexical modes remain explicit. Migrate every current parser before resuming new families. This is a decomposition of one migration, not an optional pilot.
3. **LALRPOP line forwarding or runtime retry/fallback to old parsers.** Cheap initial admission but leaves the current syntax machinery authoritative, doubles ambiguous behavior, and conceals missing cutovers. Reject. A test-only frozen comparator can exist during a cutover; old production syntax code must be removed when that family switches.

All choices below are recommendations grounded in repository evidence, not additional owner decisions. No fresh user clarification is needed for the architectural direction.

## Existing entry and preservation boundary

The public entry is `pub fn render(source: &str, options: &RenderOptions) -> Result<RenderedDiagram, RenderError>` at `engine/src/lib.rs:114`. Keep `RenderOptions`/`RenderLimits`/`RenderedDiagram`/`RenderError` and the measurement exports unchanged (`lib.rs:9`, `:25`, `:48`, `:56`, `:68`).

Only parsing and its internal adapters should change. Keep the deterministic session, callback controls, text caches, resource policy and terminal SVG pipeline at this boundary.

## Recommended module layout

Add `engine/src/plantuml/parser/` containing `mod.rs` (private orchestration), `token.rs`, `lexer.rs`/small family mode modules, `span.rs` or reuse `origin::SourceSpan`, `error.rs`, `arena.rs`, and `grammar/`. Generated output belongs to `engine/src/plantuml/generated/`, included behind narrow generated-code lint/rustfmt exemptions. Exact subdivisions can be adjusted for the repository's small-function guidance; the important boundary is typed grammar output, not file count.

Recommended grammar inputs: `document.lalrpop`, `definition.lalrpop`, `preamble.lalrpop`, `sequence.lalrpop`, `uml.lalrpop`, `chen.lalrpop`, `state.lalrpop`, `activity.lalrpop`, `tree.lalrpop` (separate mindmap/WBS entrypoints), `json.lalrpop`, `yaml.lalrpop`, `hcl.lalrpop`, `timing.lalrpop`, `gantt.lalrpop`, `salt.lalrpop`, `nwdiag.lalrpop`, `files.lalrpop`, `packet.lalrpop`, `board.lalrpop`, and `creole.lalrpop`. Common declaration/arrow/preamble fragments must be reused by an explicit deterministic generation mechanism or a small shared grammar with typed entrypoints; LALRPOP files should not be assumed to have an unverified cross-file production-import facility. Start with small explicit duplicated common productions if necessary and audit/test their agreement; do not invent a macro preprocessor to avoid a few rules.

Keep family semantic builders beside existing models initially. Rename/restructure existing `Parser` types into `Builder` only after removing their source-text dispatch. A builder may accept `Declaration`, `Relation`, `Condition`, `Property`, etc.; it must not accept a whole raw command and resplit it. Existing `*scene.rs`, `graph.rs`, `stategraph.rs`, `activitytile.rs`, `treescene.rs`, `text.rs`, `scene.rs`, `svg.rs`, and `chrome.rs` should see equivalent models and need no layout rewrite.

## Lexing, preprocessing, family selection, and raw ownership

**Token contract.** Use borrowed atoms/quoted lexemes and bounded owned decoded values only when necessary; retain exact start/end offsets. Emit newline and family-specific punctuation/indentation tokens. Preserve CRLF physical line mapping, BOM behavior, blank rows, leading tabs/spaces, trailing separators, quotes, escapes, colon captions and `::` names. Do not call global `trim` or discard every newline. JSON whitespace differs from HCL physical header separators; Salt rows and YAML indentation are semantic.

**Keywords are contextual.** A declaration keyword is usable as an endpoint/name where the admitted grammar permits it. Lex a word once, preserve its spelling and context, and allow the appropriate keyword terminals in `Name`/`Endpoint` productions. Do not give all keywords globally reserved status. If a lexical mode needs to know a command header to enter a raw label/body, classify the bounded header using explicit generated header productions or a documented lexical delimiter rule, not another full handwritten command parser. Arrow-looking quoted text remains quoted data.

**UML family selection is not a parsing fallback.** `mod.rs:154` and `uml::is_graph` (`uml.rs:131`) currently choose among sequence/UML/state/activity/timing using first decisive commands and an implicit-sequence default. Preserve those admitted outcomes via typed lexical/header evidence, then invoke exactly one generated family parser. Wrapper-specific families need no heuristic detection. Read-only bounded detection is acceptable orchestration; keep the behavior table explicit, with keyword endpoint, actor/database, note and `[*]` ambiguity tests. Do not retry different parsers until one happens to accept. If useful, use a generated neutral header grammar for detection, not a new universal semantic model. The final family parser must consume the entire selected body and enforce all syntax.

**One shared lexical ownership implementation.** Current `source::prepare` tracks note/action raw bodies, graph mode and timing commands (`source.rs:170+`); preprocessing independently tracks related state (`preprocess.rs:33+`). Their divergence produced the current Chen comment regression. Consolidate byte-level comment/quote/raw scanning while preserving behavior. The fix2 atomic consumption of comment opener/closer bytes is a required baseline. A two-character delimiter cannot reuse either byte as a second delimiter; comment text must remain inert for expansion/capability scans. Explicit raw-note/action/data ownership keeps comment-looking characters literal. Preserve current physical-line versus expanded-terminator behavior (`preprocess.rs:168–184`) and its regressions.

**Document grammar.** Replace wrapper pairing/single-document/empty-body/trailing-input state machines in `source::prepare_document` and `source::prepare` (`source.rs:28`, `:170`) with actual generated wrapper productions plus lexical trivia. The generic document layer may return a spanned opaque body region because the *selected generated family grammar* consumes that region completely. It may not treat the entire language as arbitrary lines. Reject output filenames/suffixes as before; never turn wrapper suffixes into output paths. Preserve wrapper case rules rather than globally normalizing every family. Validate EOF lexical state after the closing wrapper too (assigned Gantt repair).

**Preprocessing is evaluation, not a family parser.** Retain the bounded eager immutable literal substitution engine, name registry, no inserted-text rescan, expansion provenance, capability policy and use/definition storage (`preprocess.rs`, `origin.rs`). Move admitted `!define` declaration syntax/name/literal boundary to `definition.lalrpop`, and wrapper/front-matter placement recognition to generated document/preamble syntax. The evaluator may iterate physical source fragments, but must not remain an alternate hidden grammar for family commands. An original-source lexical pass and an expanded-source lexical pass are both needed: a substituted note/action terminator controls the next row, while the current row's authored raw ownership is already established. Generated wrapper/directive manufacture remains rejected. Full TIM functions, procedures, assignments, conditionals, loops, includes, environment/time/filesystem/network builtins stay denied; do not add them just because a parser generator can express them.

This sequencing requires a dedicated shared-front-end increment and tests, not a naive “preprocess all strings, then parse” replacement. Preserve `Document::check_preamble`'s actual invariant (definitions before the first family statement and outside styles, `origin.rs:64`), but replace its dependence on normalized `Line` indices with parsed boundary spans when the adapter is removed.

**Styles and chrome are in scope.** `style.rs` is substantial handwritten grammar today: preamble scanning (`:106`), region alignment/colon/body (`:177`, `:252`), skinparam key/value (`:292`), stylesheet braces/selectors/declarations (`:322`). Put all admitted structures into generated productions. Preserve `Preamble`, effective font propagation, last region per role, no mixed skinparam/style forms, supported root/element/document/region targets, finite properties, case rules and 6–96px validation. `style::color` and typed property application remain semantic validation, not source grammar. `chrome::compose` is layout and remains. Late chrome rejection must use complete grammar shapes and ownership: YAML `title:` keys, HCL blocks named `title`, and nwdiag server names are data in the appropriate context. HCL continues to reject shared styles/chrome rather than acquiring them accidentally.

**Creole is also in the completion scope, but it is a separate label grammar.** Do not claim all handwritten PlantUML parsing was removed while leaving `creole::runs`' nesting parser unchanged. Preserve the lexical stage for escape/URL awareness, symbols, tags and line breaks (`creole.rs:54`); preserve bounded delimiter-pair eligibility analysis (`:197`) as a lexical disambiguation step because unmatched symbols are currently literal. Replace styled-span nesting/syntax recognition (`:220`) with generated label productions. Typed run building/coalescing and effective font/decorations remain semantic work. Preserve same-line symbol pairing, tag-versus-symbol matching, crossed/empty/duplicate span rejection, literal unpaired marks, blank-line behavior, and unsupported paired wave/mono/rich-text/image/link/math policies. Generated grammar must not reinterpret plain `<`, URL `//`, or escaped punctuation as resources. Literal data rendering stays literal: no unexpected Creole activation in JSON/YAML/HCL values.

**JSON/YAML are in scope even though they are data languages.** They are custom handwritten PlantUML parsers, so merely feeding old `parse_json`/`yaml::parse` from LALRPOP is not a cutover. JSON structural productions preserve strict syntax, duplicate object entries, exact finite number spelling and current exponent bounds. Primitive string escape decoding can reuse the existing audited `serde_json` function. YAML is the admitted PlantUML subset, not YAML 1.2 generally: scalars remain strings, tab handling and literal-block trimming follow current behavior, duplicate keys replace values in original position, narrow flow/list-of-map handling and prohibited tags/anchors/aliases/folded blocks remain explicit. Preserve the pre-model capability admission principle at `yaml.rs:31`: token/ownership validation must finish before building any value model. No general YAML library change is required.

## Budgets, spans and errors are part of the parser design

`Budget::{checkpoint,charge,item,depth,text}` are the current accounting interface (`budget.rs:25–62`). Default limits in `lib.rs:34` remain 256KiB source, 16MiB SVG, 10,000 model items, depth64, 5,000,000 work, 10s cooperative deadline; the host's independent process safeguards remain unchanged. Lexer scans, decoded strings, tokens, syntax nodes, semantic nodes, lookup comparisons, indentation/owner stacks and grammar reductions must be charged/bounded before their allocations/appends. Do not use a “charge after parse” audit. Keep label/token caps and checked arithmetic.

Recommended mechanism:

1. Validate custom limits and source before lexing, as today. Charge each bounded scan chunk and check cancellation during scans, including discarded whitespace/comments and raw literal chunks.
2. Materialize borrowed token events only after charging their retention and checking a documented token/stack-work bound derived from validated source/work limits. Keep syntax accounting distinct from retained semantic `model_items` where necessary to avoid arbitrarily multiplying existing model limits. Count generated AST storage explicitly; prefer arena handles/reused typed nodes over a duplicate source-string AST.
3. Before entering the generated parser, reserve/check a conservative upper bound for its internal stacks and reductions from the actual bounded token count, nesting and a reviewed per-grammar constant. Audit the generated automaton: no nullable recursive cycles, no unbounded epsilon action loops, no recovery-token accumulation, and no uncharged long string/list concatenation. Left-recursive bounded list append or an arena chain avoids right-recursive O(n) pending lists and O(n²) concatenation.
4. Every retaining grammar action uses a fallible helper (`=>?`); list growth and node construction charge before `push`/copy. Depth checks must run on opener/indent admission, before shifting/building arbitrarily deep contents, not only when reducing a completed subtree. Lexical nesting counters are a guard; the grammar still validates legal structure. For constructs whose opener cannot be decided lexically, use a generated prefix/open reduction plus a bounded parser-stack admission ceiling.
5. Reduction/build helpers and token iterator checkpoints propagate cancellation as `ParseError::User` carrying the existing typed cancellation/limit error. Check before/after parsing and callbacks. Do not turn cancellation into EOF then report a syntax error.

This extra stack gate is necessary: the cached `lalrpop-util-0.23.2/src/state_machine.rs:204` contains internal state/symbol vectors and `:263–264` pushes them. LALRPOP itself does not automatically call this project's budget on every shift. Use conservative pre-admission plus audited action/iterator checkpoints; do not falsely state that `=>?` alone bounds generator-owned allocations. The fixed initial stack allocation is included in the upfront reservation. If the first grammar cannot demonstrate a bound/checkpoint interval from generated code, fix that infrastructure before releasing later cutovers; the hard worker watchdog is not an excuse to omit engine-side bounds.

Locations should be expanded UTF-8 byte offsets mapped back through `origin::Document` segments. Existing `SourceSpan` already has byte range plus one-based authored line/UTF-8-byte column (`origin.rs:7`); `Origin::Expansion` stores use span and definition ID (`:27`). Preserve compact ancestry, bounded error candidates and direct versus generated origin. Add an internal structured parse failure carrying offending span/feature/error category, then format once at the public `RenderError` boundary. Existing `invalid`/`unsupported` hardcode column1 (`budget.rs:78`) and `Document::map_error` interprets formatted messages (`origin.rs:110`); new precise parser errors should map spans directly instead of relying on fragile string reparsing. Layout label errors can retain current honest bounded-candidate behavior until label-span metadata is available; do not invent an exact unique source location from repeated label text.

Preserve error variants for unsupported capabilities, malformed syntax, bounds and cancellation. Bound offending lexeme/expected-token lists in diagnostics; the generated terminal set is finite but dumping every terminal is not a useful user error. No recovery-and-render of partial diagrams. Reject trailing input/suffixes at EOF. Better precise columns are compatible; silently accepting previous negative cases is not.
