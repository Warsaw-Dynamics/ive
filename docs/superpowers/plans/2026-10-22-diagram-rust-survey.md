# Rust diagram survey and GPUI dependency check

Research date: 2026-10-22. Read-only investigation for handoff items 7–8. The initial survey performed no product code changes, downloads, benchmarks, adoption, or compatibility tests. The later puml audit cloned and built a pinned release in `/tmp`, ran narrow behavior checks, and is distinguished below. Coverage and test figures below are upstream claims unless explicitly identified as local observations. A family name in a README is not evidence of full syntax or visual parity. No PlantUML GPL repository was read; local PlantUML observations use only `/mnt/data/Projects/plantuml-mit/src`.

Final selection (2026-10-23): the workspace uses audited Merman 0.9.2 for Mermaid and an authorized MIT 1.2026.9 native PlantUML translation. The earlier conditional `puml` recommendation below was superseded by its [source-lineage adoption hold](2026-10-23-puml-provenance-audit.md). Actual delivered subsets and limits are in [COVERAGE.md](../../../diagram-ports/COVERAGE.md).

## Decision-relevant findings

Several substantial native Rust diagram implementations now exist. The first engineering milestone should audit their behavior and provenance against the pinned Mermaid 12.2.0 and PlantUML MIT 1.2026.9 references. A fresh implementation remains appropriate for behavior not covered by an acceptable dependency, but a plan should not assume the ecosystem has only parsers or server wrappers.

For Mermaid, Merman is the strongest initial audit candidate because its documentation describes pinned-source comparisons, host text measurement, a resvg-safe pipeline, family-specific residuals, and explicit component provenance. Its default ELK feature closure is incompatible with the current project policy; it documents ways to omit ELK. mmdr, rusty-mermaid and Selkie are useful independent candidates. For PlantUML, the follow-up puml audit supports an experimental backend after hardening; it does not establish complete PlantUML equivalence or safe unchanged handling of arbitrary input.

The user subsequently permitted other dependencies and asked to try full ports, with a standalone viewer first and Mermaid before PlantUML. Use audited permissive dependencies where they help, keep engines independent of GPUI, and treat the viewer as the first integration milestone. Full port remains the objective; initial family slices and experimental backends must be named honestly.

## Practical adoption/audit gate

With additional dependencies authorized, pin candidate commits and perform a 1–3 engineer-week comparison before choosing a fork. Use the same fonts, Mermaid 12.2.0 source and MIT PlantUML edition across all comparisons. Start with owner documents plus deliberately difficult fixtures: nested subgraphs and cross-cluster edges, self/multiple/cyclic edges, escaped and multiline text, non-ASCII/RTL, sequence groups/activation, class compartments/generics, themes/directives, invalid input and resource limits. Record parser coverage separately from model and geometry fidelity. Verify the full selected Cargo feature/dependency graph and embedded resources against `deny.toml`; root MIT/Apache metadata alone is insufficient.

For Merman, start with `default-features = false` and the minimum required diagram/SVG features from the matching revision; the moving README gives `all-diagrams` + `svg` as a basic no-optional-engine/math recipe. Use the resvg-safe pipeline and host measurement API. Check that another package has not re-enabled `merman-elk-layered`; features are additive. Review the [component inventory/notices](https://github.com/Latias94/merman/blob/main/THIRD_PARTY_NOTICES.md), including MIT Dagre translations in `dugong` and Cytoscape/FCoSE translations in `manatee`. These could eliminate sizeable original translation work, but the current project is still an upstream-dependent evolving codebase, not a fidelity certificate.

Adapted implementations and resources still need notices and source traces. Do not copy ELK code from any port under the assumption that a permissive facade relicenses it. The follow-up puml audit is recorded at `/tmp/ive-puml-audit.md`; reusable source checkout is `/tmp/ive-puml-audit.V9qwLm/puml`. No complete candidate parity suite was run. Basic sequence/class/component/activity SVG generation was verified for puml, along with its IO and raw-SVG traps. Its public compile options do not propagate to the second model parse; a controlled adapter/fork is required.

## Item 8: embedding alternatives, comparison only

### TeaVM PlantUML

TeaVM compiles Java bytecode ahead of time, with JavaScript and other targets; its [official overview](https://teavm.org/docs/intro/overview.html) cautions that reflection, resources, JNI and classloading need adaptation. The inspected MIT source already has substantial adaptation. In particular, `teavm/DiagramRendererTeaVM.java:144` describes a headless, DOM-free/AWT-free path, implemented with `StringBounderFromWidthTable` and `UGraphicSvg`; it is wrong to assume every TeaVM path requires a browser. Its deterministic width tables would also be useful reference behavior for Rust tests.

The browser path is different: `teavm/js/SvgGraphicsJs.java:389,643,658,671,724,860` uses document/SVG creation, XMLSerializer, canvas metrics, SVG getBBox and DOMParser. `GraphVizEngineJs` bridges Viz.js WebAssembly and documents a Smetana fallback when Viz is absent. An embedded engine would need the chosen headless entry point, explicit resources and bounded execution; bundling the browser entry point requires a much larger host API. MIT release sources contain generated MIT license headers alongside retained original comments: use the distributed MIT artifact and notices as provenance, not another edition's repository.

Estimated effort, not measured: 2–4 engineer-weeks for a limited headless JS/native embedding spike; 4–10+ weeks for production offline/resource/cancellation/FFI/package hardening and a representative cross-family regression corpus, assuming the MIT edition can reproduce its TeaVM build. A Wasm route additionally requires confirming target ABI, imports, supported Wasm features and usable Rust runtime; the existence of a TeaVM directory does not prove a ready portable Wasm artifact. The source explicitly marks the C backend experimental (`TeaVM.java:166`).

Binary size and speed were not measured. Planning allowance only: compiled PlantUML plus resources and an embedded modern JS/Wasm engine is plausibly megabytes to tens of megabytes, not the few-kilobyte runtime headline; an actual build is necessary before quoting totals. Interpretive JS execution, Java-object allocation and bridge calls may cost more than Rust, but removing JVM/browser process startup can still help. No defensible multiplier is available from this inspection.

### MQuickJS / modern JS runtime

[MQuickJS's own README](https://github.com/bellard/mquickjs/blob/main/README.md) advertises roughly 100 kB ROM including libc on ARM Thumb-2 and programs using 10 kB RAM, with speed comparable to QuickJS. Those are engine/embedded-platform figures, not a Mermaid or desktop diagram artifact. It supports a strict mostly-ES5 subset: hole-free arrays, restricted eval, ASCII case transforms, Date.now only; modern language/runtime capabilities cannot be assumed. MIT licensed.

Mermaid 12 uses ES modules, async code, collections and browser services across its dependency graph. ES5 transpilation alone does not restore missing runtime semantics or provide DOM/SVG/font layout, and MQuickJS does not supply those services. The headless TeaVM path reduces DOM needs for PlantUML, but generated JS must still be checked against the strict subset. Browser Viz additionally needs a Wasm host/runtime, so MQuickJS alone is insufficient.

Estimated effort: 1–2 engineer-weeks for a compatibility experiment; 6–16+ weeks for a useful, bounded Mermaid host after switching to a modern embedded JS engine and replacing/browser-hosting DOM/text operations; broad parity is open-ended. Tiny DOM mocks that pass simple flowcharts do not establish full support. A modern QuickJS engine is a more realistic JS baseline than MQuickJS, but still adds C/FFI, runtime and polyfill integration. These alternatives do not displace the owner's native Rust direction.

## GPUI: can the standalone app literally have one direct dependency?

Locally verified against IVE's exact pinned source, resolved read-only with `cargo metadata --offline --locked`: `/home/kb/.asdf/installs/rust/1.99.0/git/checkouts/pgui-ec323d2a127f3321/f5d5fa2`, revision `f5d5fa2f8f07b0be68442e694d22ed6064609e73`, not the different `/mnt/data/Projects/gpui-zed-main` checkout.

- IVE `Cargo.toml:29–30` declares both `gpui` and `gpui_platform` from the same Warsaw-Dynamics/pgui revision. `src/main.rs:174` starts with `gpui_platform::application()`.
- Core `crates/gpui/src/app.rs:182` exposes `Application::with_platform(Rc<dyn Platform>)`, not a zero-argument `Application::new()` desktop constructor. `new_inaccessible` also requires a platform.
- Core `gpui.rs:37,197` re-exports platform abstractions; it does not re-export OS backend implementations or `gpui_platform::application`. `gpui/Cargo.toml:181` includes `gpui_platform` only as a development dependency for its examples/tests. Dependency dev-dependencies do not become a consumer's normal dependencies.
- `crates/gpui_platform/src/gpui_platform.rs:14` constructs `Application::with_platform(current_platform(false))`; `current_platform:79` chooses Linux/macOS/Windows/iOS/web implementation crates. `gpui_platform` re-exports only `gpui::Platform`, not the entire GPUI API. Depending solely on `gpui_platform` does not make `use gpui::...` available in consumer Rust code, and does not re-export the core widget/types API.
- The pinned `gpui/examples/hello_world.rs:10` imports `gpui_platform::application` alongside `gpui` types. `gpui`'s x11/wayland feature names alone do not add a platform constructor to the core API.
- Text/shaping and SVG facilities are in core: `gpui.rs:219,225` re-export SVG renderer/text-system APIs; `Application::text_system` at `app.rs:333` returns `Arc<TextSystem>`, and `TextSystem::shape_line` is public at `text_system.rs:646`. GPUI already internally depends on resvg/usvg, but their transitive existence does not expose their crate names as direct Rust imports.

Conclusion: with this unchanged fork, a normal runnable cross-platform standalone app cannot use only the core `gpui` package as its sole direct dependency. It needs a real platform implementation. Implementing all OS backends inside the app to avoid the platform crate is technically possible but entirely disproportionate and contrary to the intent.

The current user permission removes a literal one-dependency constraint: use `gpui` and `gpui_platform` from the same repository/revision, plus audited dependencies for engines as appropriate. Keep the exact two-package bootstrap fact visible in the standalone viewer design. A facade or older GPUI revision is unnecessary. Engines should remain GPUI-independent so they can be tested separately.

## Engineering estimates for the native port direction

These are order-of-magnitude engineering-effort estimates, not calendar commitments, throughput measurements or claims about how fast agents can work. They assume deterministic differential tests, bounded hostile-input handling, selected theme/config compatibility, real text measurement and ordinary review. Agent parallelism can accelerate separate families after common interfaces stabilize; parser generation and code volume do not substitute for parity diagnosis.

| Scope | Estimated effort | Exit evidence |
| --- | --- | --- |
| Candidate/provenance audit and parity harness | 1–3 engineer-weeks | Pinned candidate matrix, verified permissive closure, owner corpus comparison, documented gaps |
| Standalone GPUI host and one narrow Mermaid end-to-end slice | 2–5 engineer-weeks | Offline app renders deterministic source with diagnostic failures; SVG/text host integration exercised |
| Mermaid flowchart + sequence + class with credible common syntax | 10–20 engineer-weeks total from a fresh engine | Explicit grammar/config coverage, compound/cyclic/layout fixtures, semantic/geometry/raster checks and resource bounds |
| Broad Mermaid 12.2 family coverage with documented residuals | 40–100 engineer-weeks total from a fresh engine | Every inventory family has feature coverage and pinned upstream comparisons; no silent fallback success |
| PlantUML sequence/class/component/activity and shared foundation | 20–45 engineer-weeks after usable shared drawing infrastructure | Preprocessor boundary, text/style/drawing layer, class/component clustered layout and activity/sequence fixtures |
| Broad PlantUML MIT 1.2026.9 port including its large shared infrastructure | 100–250+ engineer-weeks total | Complete inventory ledger with supported/unsupported branches and reference checks; includes difficult preprocessing, styling, layout and special families |
| Dot-compatible compound layout, if unavailable permissively | 12–30+ engineer-weeks, substantially shared with PlantUML estimate | Rank/ordering/coordinate/routing/cluster tests against reference; explicit version/fidelity boundaries |

The broad estimates have at least factor-of-two uncertainty. Full parity for arbitrary upstream plugins, every font, image resource, math/hand-drawn output and browser-specific HTML may exceed them or require explicit exclusions. Existing audited permissive ports can reduce work substantially; the current permission to use dependencies should be used to avoid unnecessary translation. A three-parser demo must be labelled an initial slice, never a completed Mermaid or PlantUML port.
